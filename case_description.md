# РасходМенеджер — учёт личных финансов 

> Уровень: 1–2 курс. Бэкенд: Python / Node.js / Go / C++ (выбор команды).
> БД: Postgres или MongoDB. Фронтенд: React + TypeScript, сборка Vite.
> Семестр (16 недель), команда 2–4 человека. Код — на Sourcecraft.
> Авторизация в скоуп не входит.

## 1. Одно предложение

Веб-приложение для записи личных доходов и расходов по категориям с балансом,
фильтрацией по периоду и категории и итогами по категориям.

## 2. Для чего это нужно

Человек хочет видеть, куда уходят его деньги: сколько пришло, сколько ушло,
по каким категориям и в какие периоды. Внешние сервисы требуют регистрации
и хранят данные у себя — здесь пользователь полностью владеет своими данными.
Результат — настоящий небольшой продукт с сервером и базой данных, на котором
команда учится связке «React-интерфейс → REST API → запросы к БД» целиком,
а не по отдельности.

## 3. Что проверяет проект

1. Проектирование схемы данных: сущность, поля, ограничения.
2. Работа с БД из бэкенда: CRUD, параметризованные запросы, агрегаты (SUM, COUNT).
3. REST/JSON API: спроектировать и реализовать 6–10 эндпоинтов.
4. React + TypeScript: компоненты, состояние, работа с API (fetch/axios).
5. Валидация ввода на бэкенде (суммы, даты, категории).
6. Агрегация в запросах к БД: баланс и итоги по категориям считаются запросом, а не в коде приложения.
7. Понимание архитектуры: команда объясняет поток данных своего проекта по `ARCHITECTURE.md`.
8. Работа в команде: распределённая Git-история на Sourcecraft.

## 4. Функциональные требования

Все операции выполняет единственный пользователь приложения (без
авторизации — осознанное упрощение, см. раздел 8).

1. **Добавление транзакции**: пользователь заполняет форму (тип «доход /
   расход», категория, дата, сумма) и сохраняет. Транзакция появляется
   в списке, баланс пересчитывается.
2. **Удаление транзакции**: пользователь удаляет транзакцию после
   подтверждения (модальное окно или отдельный шаг подтверждения).
3. **Баланс**: на главной странице отображается текущий баланс — сумма
   всех доходов минус сумма всех расходов. Баланс вычисляется запросом
   (SUM), не хранится.
4. **Фильтрация по периоду**: пользователь задаёт дату «с» и дату «по» —
   список показывает только транзакции за этот период.
5. **Фильтрация по категории**: пользователь выбирает категорию из
   выпадающего списка (или «все») — список показывает только транзакции
   этой категории.
6. **Итоги по категориям**: отдельный экран/блок показывает таблицу
   «категория → сумма» за выбранный период. Итоги вычисляются запросом
   (SUM с GROUP BY), не хранятся.
7. **Сортировка списка**: по дате — по убыванию (свежие сверху) по
   умолчанию; переключение на возрастание.

Ограничения полей: «сумма» — положительное число с точностью до копеек
(больше 0 и не больше 10 000 000, не более двух знаков после запятой);
«дата» — корректная календарная дата, не из будущего; «категория» —
значение из фиксированного списка; «тип» — только «доход» или «расход».

## 5. Данные (БД)

- **Сущность «транзакция»**: id, тип (доход/расход), категория, дата,
  сумма, дата создания записи. Состав неключевых полей команда может
  расширить — решение команды.
- **Категории: фиксированный список в коде бэкенда** (10–15 значений:
  «продукты», «транспорт», «жильё», «зарплата» и т.п.). Отдельной
  таблицы/коллекции категорий и CRUD для них нет — это осознанное
  упрощение; фронтенд получает список категорий эндпоинтом.
- **Сумма хранится как число** (в копейках целым числом или decimal —
  решение команды с обоснованием в `ARCHITECTURE.md`) и не вычисляется.
  Баланс и итоги по категориям — вычисляются запросом (SUM), не хранятся.
- **Даты**: дата транзакции вводится пользователем (поле date в форме);
  дата создания записи проставляется бэкендом автоматически (UTC),
  в форме её нет.
- **Seed-скрипт обязателен**: создаёт структуру данных и наполняет
  30–50 транзакциями за последние 2–3 месяца с разными типами,
  категориями, суммами (включая крайние значения) и датами (включая
  границы месяцев).

## 6. Бэкенд

Бэкенд — это и веб-сервер (отдаёт статику собранного фронтенда), и слой
работы с базой данных. Сложность — простая, без скрытых усложнений.

- Язык и фреймворк — выбор команды (Python / Node.js / Go / C++),
  фиксируются в `ARCHITECTURE.md` с кратким обоснованием. БД — Postgres
  или MongoDB.
- Эндпоинты (ориентир, допускается корректировка с обоснованием в
  `ARCHITECTURE.md`):

| Метод | Путь | Действие |
| --- | --- | --- |
| GET | `/api/transactions` | список с фильтрами по периоду/категории + сортировка |
| POST | `/api/transactions` | добавить транзакцию |
| DELETE | `/api/transactions/{id}` | удалить транзакцию |
| GET | `/api/balance` | текущий баланс (SUM доходов − SUM расходов) |
| GET | `/api/summary` | итоги по категориям за период (SUM + GROUP BY) |
| GET | `/api/categories` | список категорий для формы |

- Фильтрация, сортировка и агрегация — **в запросах к БД** (WHERE/
  ORDER BY/GROUP BY/SUM в SQL или операторы запроса и aggregation
  pipeline в MongoDB), не в коде приложения. Баланс — SUM по типам
  в одном или двух запросах.
- Все запросы с пользовательским вводом — параметризованные; склейка
  строк запроса с вводом запрещена (см. раздел 8).
- Ошибки валидации возвращаются структурированно (код ошибки + список
  полей с сообщениями); HTTP-статусы корректные (400 — ошибка ввода,
  404 — транзакция не найдена). Падение сервера на вводе пользователя
  недопустимо.
- Зависимости фиксируются манифестом (requirements/pyproject,
  package.json, go.mod или CMakeLists — по языку).

## 7. Фронтенд

- React + TypeScript, сборщик Vite (или другой популярный актуальный —
  фиксируется в `ARCHITECTURE.md`). Собранная статика отдаётся бэкендом.
- Экраны: список транзакций-таблица (с балансом и счётчиком записей),
  форма добавления транзакции, экран итогов по категориям,
  подтверждение удаления.
- Реестр транзакций — таблица (дата, тип, категория, сумма, действия).
  Доходы и расходы визуально различаются (например, цветом суммы).
  Фильтры — панель над таблицей; состояние выборки отражается в URL
  (query-параметры), чтобы выборку можно было перезагрузить и шарить
  ссылкой.
- Данные загружаются через API бэкенда (fetch/axios); ошибки валидации
  показываются рядом с полями формы.
- Читаемый базовый вид: рамки таблицы, отступы, выделение итогов.
  UI-библиотеки не обязательны, пиксель-перфект не требуется.

## 7а. Архитектура и поток данных

- В репозитории на Sourcecraft — **`ARCHITECTURE.md`**, фиксирующий все
  основные принятые решения: язык и фреймворк бэкенда, БД, сборщики
  бэкенда и фронтенда (каждый выбор — с кратким обоснованием), схема
  данных, список эндпоинтов, поток данных.
- Диаграмма потока — **mermaid прямо в `ARCHITECTURE.md`**: React-
  приложение → HTTP/JSON → бэкенд → БД, с указанием выбранных технологий
  и направлений запросов/ответов. Документ обновляется при изменении
  архитектуры.
- На защите команда объясняет путь запроса: от нажатия «Добавить
  транзакцию» в React до записи в БД и пересчёта баланса на экране.

## 8. Безопасность

- Авторизация в скоуп не входит: приложение однопользовательское, ролей
  и систем входа нет. Это осознанное упрощение, указано в README.
- Параметризованные запросы к БД везде, включая фильтрацию по периоду
  и категории (в MongoDB — параметризованные операторы).
- Экранирование вывода: пользовательский текст не вставляется в разметку
  как HTML; `dangerouslySetInnerHTML` не используется.
- Валидация — на бэкенде; фронтенд-валидация не считается защитой.

## 9. Алгоритмы и проверки

Алгоритмические места: агрегация баланса и итогов по категориям
(SUM/GROUP BY с условием по типу), построение динамического условия
выборки из выбранных фильтров (период + категория, параметризованно).

Обязательные проверки корректности (часть чек-листа приёмки):

1. После добавления дохода 1000 и расхода 400 баланс = 600; после
   удаления расхода баланс = 1000.
2. Сумма 0, отрицательная, «12,5 руб» (нечисловое) и с тремя знаками
   после запятой — отклоняются сообщением у поля, данные не сохраняются.
3. Дата из будущего — отклоняется сообщением у поля.
4. Фильтр «продукты» + период «1–15 октября» показывает только
   транзакции категории «продукты» с датами в этом диапазоне.
5. Итоги по категориям сходятся с балансом: сумма итогов по расходным
   категориям равна сумме расходов в списке.
6. Удаление отменено — транзакция остаётся; подтверждено — исчезает
   из списка, баланс пересчитался.

Граничные случаи: пустой список (дружелюбный пустой экран, не ошибка),
транзакция ровно на границе периода (дата «с» и дата «по» включаются
в выборку — поведение зафиксировать), месяц без транзакций в итогах,
баланс ровно 0.

| Этап | Недели | Содержание | Артефакт сдачи |

| 1. Скелет | 1–3 | Схема БД, каркас бэкенда с пустыми эндпоинтами, каркас React, `ARCHITECTURE.md` с решениями и mermaid-схемой, seed-скрипт | Репозиторий на Sourcecraft + `ARCHITECTURE.md` |
| 2. CRUD | 4–7 | Добавление и удаление транзакций, формы React, валидация | Рабочий CRUD на seed-данных |
| 3. Логика и агрегаты | 8–12 | Фильтры по периоду и категории, баланс, итоги по категориям, динамическая выборка, безопасность | Полный функционал |
| 4. Доводка и защита | 13–16 | README с инструкцией запуска, вычитка, подготовка демо | Финальный репозиторий + README + демо |

Сдача:

- Репозиторий на Sourcecraft с Git-историей от всех участников — коммиты
  по мере работы; один коммит в конце семестра — сигнал, что работала
  не команда.
- README по схеме «клонировать → установить зависимости → поднять БД →
  seed → собрать фронтенд → запустить бэкенд → открыть в браузере».
  **Деплой в облако не требуется** — достаточно локального развёртывания
  по инструкции (вручную или docker compose, на выбор команды).
  Преподаватель запускает проект по инструкции за 10 минут; если не
  получается — это дефект сдачи.
- Демо на защите 10 минут: все проверки из раздела 9 вживую + объяснение
  потока данных по `ARCHITECTURE.md`.

## 11. Ожидаемый результат

- **Зачёт**: все 7 фич раздела 4 работают; проверки 1–6 из раздела 9
  проходят; проект запускается по README; проверяемые навыки раздела 3
  демонстрируются; команда объясняет архитектуру по своей диаграмме.
- **Сверх зачёта (звёздочки, необязательно)**: экспорт текущей выборки
  в CSV; итоги по месяцам (тренд по периодам, вычисляется запросом);
  редактирование транзакции; деплой в облако.
- **Анти-результат** (незачёт по объёму даже при «работающем» сайте):
  баланс или итоги хранятся в поле вместо вычисления запросом;
  фильтрация/агрегация сделаны в коде приложения по всей выборке;
  запросы к БД собираются конкатенацией строк; проект не запускается
  по README; коммиты только одного участника; команда не может объяснить
  собственный поток данных.
