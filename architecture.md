# Архитектура проекта: Выбор стека и структура БД

## 1. Выбор технологий

Для реализации backend-части проекта выбран следующий стек: **Go (Golang)**, фреймворк **Gin** и ORM **GORM**.

### Почему Gin?
Среди рассмотренных вариантов (`net/http`, `Chi`, `Gin`, `Echo`) выбор пал на **Gin** по следующим причинам:

**Главные преимущества:**
*   **Высокая скорость работы:** Gin построен на базе кастомного роутера (httprouter), что обеспечивает высокую производительность.
*   **Удобный API:** Наличие `gin.Context` объединяет информацию о запросе и методы ответа, упрощая код обработчиков.
*   **Встроенные инструменты:** Есть готовые механизмы для биндинга JSON (`ShouldBindJSON`), валидации данных и группировки маршрутов (`RouterGroup`).
*   **Популярность:** Огромное сообщество и множество готовых middleware.

**Недостатки:**
*   **Частичная совместимость с net/http:** Использует собственные типы контекста и хендлеров, что требует адаптации при использовании стандартных библиотек Go.
*   **Меньший контроль:** Часть низкоуровневой логики HTTP скрыта за абстракциями фреймворка.

---

### Почему GORM?
Для работы с базой данных выбрана библиотека **GORM**.

**Главные преимущества:**
*   **Удобство разработки:** Позволяет работать с БД через Go-структуры, не написывая сырой SQL для типовых операций (CRUD).
*   **Поддержка связей:** Легко описываются отношения между таблицами (Has One, Has Many, Many to Many).
*   **Хуки и транзакции:** Встроенная поддержка жизненного цикла объекта и атомарных операций.
*   **AutoMigrate:** Возможность автоматически создавать таблицы на основе структур (удобно для разработки).

**Недостатки (важно учитывать):**
*   **«Магия» и рефлексия:** Поведение часто скрыто в соглашениях (convention over configuration). Сложно предсказать итоговый SQL-запрос без логов.
*   **Ошибки только в рантайме:** Поскольку запросы строятся динамически (через строки или методы), опечатки в именах колонок не ловятся компилятором.
*   **Производительность:** Рефлексия добавляет накладные расходы. В высоконагруженных узлах GORM может быть медленнее чистого SQL или `sqlc`.
*   **Сложные запросы:** Для агрегаций, оконных функций и сложных JOIN-ов приходится использовать `Raw SQL`, что снижает преимущества ORM.
*   **AutoMigrate не для продакшена:** Он не умеет безопасно удалять колонки или вести историю миграций. Для production-среды обязательно использовать инструменты вроде `golang-migrate` или `goose`.

## 2. Схема базы данных

Ниже представлена структура базы данных для учета финансовых операций.

### Описание связей
*   **Profiles → Transactions:** Один профиль может иметь много транзакций (1:M).
*   **Categories → Transactions:** Одна категория может быть использована во многих транзакциях (1:M).
*   **Currencies → Transactions:** Одна валюта может фигурировать во многих транзакциях (1:M).

### Текстовое описание таблиц

#### `profiles`
Таблица пользователей/профилей.
*   `id` (PK) — уникальный идентификатор профиля.
*   `name` — имя пользователя.
*   `role` — роль в системе.
*   `created_at` — дата создания профиля.

#### `transactions`
Главная таблица финансовых операций.
*   `id` (PK) — уникальный ID операции.
*   `profile_id` (FK) — ссылка на `profiles.id`.
*   `category_id` (FK) — ссылка на `categories.id`.
*   `currency` (FK) — ссылка на `currencies.code`.
*   `type` — тип операции (доход / расход).
*   `amount_minor` — сумма в минимальных единицах (центах/копейках) для избежания проблем с плавающей точкой.
*   `occurred_on` — фактическая дата операции.
*   `description` — текстовое описание.
*   `idempotency_key` — ключ идемпотентности для защиты от повторных списаний/начислений.
*   `created_at` / `updated_at` — технические даты записи.

#### `categories`
Справочник категорий трат/доходов.
*   `id` (PK) — ID категории.
*   `code` — уникальный код категории (для использования в коде/API).
*   `name` — отображаемое название.
*   `type` — тип категории (доход / расход).

> **Важное примечание по категориям:**
> В текущей реализации категории хранятся в отдельной таблице `categories` с сидом (начальным набором данных), но без полноценного CRUD для пользователей. Это допустимое архитектурное решение, обоснованное тем, что список категорий фиксирован бизнес-логикой. Внешний ключ гарантирует целостность данных. Если потребуется строгая привязка к коду, можно хранить текстовый код категории прямо в таблице `transactions` с ограничением `CHECK`, но реляционный подход (FK) предпочтительнее для масштабируемости.

#### `currencies`
Справочник валют.
*   `code` (PK) — код валюты (например, "RUB", "USD").
*   `name` — название валюты.
*   `minor_units` — точность (количество знаков после запятой, например, 2 для рублей).
